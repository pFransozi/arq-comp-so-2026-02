Retomada da Aula 03

Do Little Man Computer ao código que escrevemos

No exercício com o Little Man Computer, acompanhamos instruções como LDA, ADD e STA sendo buscadas e executadas. Agora vamos voltar um passo: quem produz essas instruções quando programamos em uma linguagem como C?

Programa no LMC → LDA · ADD · STA → buscar · decodificar · executar
1 · Código-fonteO processador recebe o código C exatamente como nós o escrevemos?
2 · TraduçãoSe no LMC executávamos LDA, ADD e STA, de onde vêm as instruções de um programa escrito em C?
3 · ArquiteturaPor que o mesmo código-fonte pode gerar instruções diferentes para x86-64 e ARM64?

Primeira ideia

O código-fonte expressa uma intenção; a máquina executa operações mais elementares

Linguagens de alto nível nos permitem trabalhar com nomes, tipos, decisões, repetições e funções. Essas abstrações precisam ser traduzidas para operações pertencentes à máquina que executará o programa.

C · código-fontecomece simples
int soma(int a, int b) {
    return a + b;
}
A intenção é simples para nós: receber dois inteiros, somá-los e devolver o resultado.
Os nomes ajudam quem programa

No código-fonte, nomes como preco, frete e total dão significado aos dados. Depois da compilação, o processador trabalha com valores, registradores, endereços de memória e instruções — não com esses conceitos da mesma forma que nós.

int total = preco + frete; int c = a + b;

Os nomes são diferentes, mas o trabalho essencial é o mesmo: obter dois valores, somá-los e guardar o resultado.

O compilador transforma a intenção em operações da máquina

Quando escrevemos return a + b;, descrevemos o comportamento desejado. Não dizemos em qual registrador colocar cada valor nem qual instrução específica usar. O compilador toma essas decisões de acordo com a arquitetura-alvo.

return a + b;
obter a→ obter b→ somar→ retornar

No Compiler Explorer veremos que arquiteturas diferentes podem realizar esse mesmo comportamento com registradores e instruções diferentes.

Uma linha de código não corresponde a uma instrução

Não existe uma regra do tipo “1 linha de C = 1 instrução da CPU”. Uma construção de alto nível pode exigir várias operações; com otimizações, algumas delas também podem ser combinadas ou até eliminadas.

if (idade >= 18) { return 1; } return 0;

Essa decisão envolve, conceitualmente, comparar um valor, decidir qual caminho seguir e produzir um resultado. Um for pode acrescentar ainda inicialização, comparação, incremento e repetição.

Segunda ideia

O compilador precisa saber para qual máquina está produzindo código

Ao instalar um programa, talvez você já tenha visto opções como x64 e ARM64. Esses nomes não estão ali por acaso: um programa nativo precisa ser preparado para um tipo de processador capaz de entender as instruções que foram geradas.

O mesmo programa pode precisar de versões diferentes

Imagine que uma equipe desenvolveu uma única aplicação. O código-fonte pode ser praticamente o mesmo, mas na hora de distribuir o programa podem existir arquivos diferentes para computadores x86-64 e ARM64.

Isso acontece porque o código que escrevemos ainda não é o conjunto de instruções executado pelo processador. Em algum momento, a tradução precisa considerar qual máquina receberá o programa.

Qual pergunta o compilador precisa responder?

Considere novamente uma função simples:

int dobro(int x) { return x * 2; }

Para nós, a intenção é apenas receber um número, calcular seu dobro e devolver o resultado. Para o compilador ainda falta uma informação: para qual arquitetura devo gerar as instruções?

Essa informação é o target, ou alvo da compilação. Nesta parte da aula vamos isolar uma dimensão do alvo: a arquitetura do processador. Assim podemos comparar o que acontece quando o mesmo código é traduzido para x86-64 e para ARM64.
1 · FonteCódigo-fonte

É o programa que escrevemos usando as abstrações da linguagem.

2 · TraduçãoCompilador

Analisa o código e gera uma representação adequada ao destino escolhido.

3 · DestinoArquitetura-alvo

Responde para qual família de processadores estamos produzindo código.

4 · ResultadoInstruções para o alvo

O resultado usa instruções compatíveis com a arquitetura escolhida.

Target A

x86-64

Arquitetura amplamente usada em desktops, notebooks e servidores com processadores Intel e AMD.

Target B

ARM64 / AArch64

Arquitetura comum em smartphones, sistemas embarcados, computadores e servidores modernos.

Engenharia de Software

Build target

Um projeto pode gerar artefatos diferentes a partir do mesmo repositório porque cada build pode mirar um alvo diferente.

Experimento 2

Valide o que muda quando trocamos o alvo

x86-64 × ARM64

Objetivo: usar o Compiler Explorer para confirmar uma ideia já apresentada: o código-fonte e o comportamento esperado permanecem iguais, mas a arquitetura pode usar registradores e instruções diferentes.

Cmesmo nas duas compilações
int dobro(int x) {
    return x * 2;
}

Antes de abrir a ferramenta

Registradores são pequenos espaços internos usados pelo processador para manter valores durante a execução. Os nomes mudam entre arquiteturas: em x86-64 podem aparecer eax, edi ou rax; em ARM64 são comuns nomes como w0, w1, x0 e x1.

Instruções são operações disponíveis naquela arquitetura. No Assembly, normalmente aparecem no início da linha, como lea, add, lsl ou ret.

Não precisamos compreender cada instrução. Nesta atividade, vamos apenas localizar essas evidências e comparar as duas saídas.

Você encontrou nomes de registradores diferentes nas duas saídas?
As instruções geradas foram exatamente as mesmas?
Mesmo com diferenças no Assembly, o que a função continua fazendo?
A saída pode variar. Compiladores e versões diferentes podem escolher instruções diferentes mesmo para a mesma arquitetura. O que estamos validando é o padrão geral: ao trocar a arquitetura-alvo, o compilador passa a trabalhar com os recursos disponíveis naquele alvo, enquanto o comportamento pretendido pelo código permanece o mesmo.
O que mudou? Não foi o algoritmo. Mudou o vocabulário de máquina disponível para realizar esse algoritmo. Agora temos evidência suficiente para formalizar a ideia de ISA.

Formalizando o que observamos

A ISA funciona como um contrato entre software e processador

Quando o compilador produz código para um alvo como x86-64 ou ARM64, ele não pode escolher qualquer operação. O resultado precisa respeitar a Instruction Set Architecture (ISA): a interface arquitetural que define quais instruções e recursos o software pode usar ao conversar com o processador.

Pense na ISA como um acordo entre os dois lados: o software produz instruções seguindo uma especificação conhecida, e o processador implementa essa especificação para conseguir interpretá-las e executá-las.

O que esse contrato define?

Instruções disponíveisQuais operações podem ser representadas, como somar valores, comparar, desviar a execução, mover dados e acessar memória.
Exemplos: em x86-64 podem aparecer add, cmp e mov; em ARM64, add, cmp, ldr e str.
Registradores visíveis ao softwareQuais registradores podem ser usados pelas instruções e como eles são identificados. Foi isso que apareceu no Compiler Explorer com nomes diferentes em x86-64 e ARM64.
Exemplos: eax, rax e edi em x86-64; w0, x0 e w1 em ARM64.
Formato das instruçõesComo os bits de uma instrução identificam a operação e seus operandos. O Assembly é uma forma legível de representar essas instruções.
Exemplos: add eax, edi em x86-64 e add w0, w0, w1 em ARM64 mostram, de forma legível, uma operação e os registradores envolvidos.
Dados e operandosQuais tamanhos e representações de dados podem ser manipulados e como as instruções recebem os valores com os quais irão trabalhar.
Exemplos: em x86-64, eax representa a parte de 32 bits e rax a de 64 bits; em ARM64, w0 trabalha com 32 bits e x0 com 64 bits.
Acesso à memóriaComo as instruções podem localizar e acessar dados armazenados na memória.
Exemplos: em x86-64 pode aparecer mov eax, [rbx]; em ARM64, ldr w0, [x1]. Nos dois casos, a instrução está buscando um valor armazenado na memória.

Uma distinção importante

A ISA não é o processador inteiro

Dois processadores podem implementar a mesma ISA e ainda serem bastante diferentes por dentro.

  • Podem ter caches de tamanhos e organizações diferentes.
  • Podem usar pipelines e unidades de execução diferentes.
  • Podem ter frequências e quantidades de núcleos diferentes.
  • A implementação interna pode mudar sem alterar o contrato visto pelo software.
Arquitetura × organização: a ISA faz parte da arquitetura visível ao software. A organização descreve como o processador implementa esse contrato internamente. Em uma frase: a ISA diz o que a máquina oferece ao software; a organização diz como o processador realiza isso.
C · mesmo código-fonteretomando o experimento
int dobro(int x) {
    return x * 2;
}
O comportamento desejado continua sendo receber x, calcular seu dobro e devolver o resultado.

Por que o Assembly mudou?

Ao trocar o target, o compilador passa a trabalhar com outro contrato arquitetural. Em x86-64 ele escolhe registradores e instruções definidos por essa ISA; em ARM64 ele precisa escolher recursos válidos para a ISA ARM64.

Por isso o código C pode permanecer igual enquanto a representação de máquina muda. O que muda é a forma de realizar o comportamento dentro das regras da arquitetura escolhida.

1 · FonteCódigo-fonte

Expressa o comportamento desejado usando abstrações da linguagem.

2 · TraduçãoCompilador

Recebe o target e escolhe como representar o programa.

3 · ContratoISA do alvo

Define quais instruções, registradores e formas de acesso podem ser usados.

4 · ArtefatoBinário

Contém instruções produzidas para aquela arquitetura.

Engenharia de Software

Compilação

O código-fonte pode ser o mesmo, mas o processo de build precisa considerar o ambiente para o qual o software será produzido. A equipe pode precisar definir arquitetura-alvo, sistema operacional, compilador, opções de compilação e dependências compatíveis.

Decisão de engenharia: estabelecer quais plataformas o projeto suporta oficialmente e como cada artefato será construído.

Engenharia de Software

Distribuição

Depois do build, o artefato correto precisa chegar ao usuário correto. Isso afeta nomes de arquivos, instaladores, pacotes, páginas de download, documentação e o processo de release.

Uma pipeline de CI/CD pode transformar a mesma base de código em vários artefatos, como app-windows-x64.exe e app-linux-arm64.

Decisão de engenharia: organizar releases para que cada usuário consiga identificar claramente a versão adequada ao seu ambiente.

Engenharia de Software

Compatibilidade

Gerar código para a arquitetura correta é necessário, mas não é suficiente. Um programa nativo também pode depender do sistema operacional, da ABI, de bibliotecas e de runtimes específicos.

Por isso, Windows x86-64 ≠ Linux x86-64 e Windows x86-64 ≠ Windows ARM64: em cada caso alguma dimensão importante da plataforma mudou.

Decisão de engenharia: declarar e testar as combinações de plataforma que realmente serão suportadas.

Engenharia de Software

Teste e suporte

Cada plataforma adicional aumenta o conjunto de situações que a equipe precisa construir, testar e manter. Isso pode exigir ambientes de CI diferentes, testes automatizados por plataforma, tratamento de bugs específicos, documentação e suporte ao usuário.

Suportar Windows e Linux em x86-64 e ARM64, por exemplo, não significa apenas produzir quatro arquivos: significa manter confiança sobre quatro combinações de execução.

Decisão de engenharia: equilibrar alcance do produto com custo de manutenção, testes e suporte.

Visão de Engenharia de Software: a arquitetura-alvo não afeta apenas o compilador. Uma decisão tomada no build se propaga para automação, testes, distribuição, documentação, manutenção e suporte ao usuário.
A ISA é necessária, mas ainda não descreve toda a plataforma. Dois computadores podem compartilhar a mesma ISA e ainda usar sistemas operacionais e convenções binárias diferentes. É por isso que, na sequência, vamos ampliar a discussão de arquitetura para compatibilidade de software.
Atividade 3

Pesquisa aplicada: preparando uma aplicação para diferentes usuários

pesquisa · Engenharia de Software

Objetivo: investigar como arquitetura, sistema operacional, build e distribuição influenciam a entrega e a compatibilidade de uma aplicação.

Cenário: sua equipe desenvolveu uma aplicação nativa e precisa publicá-la para diferentes usuários. O código-fonte é o mesmo, mas os usuários utilizam máquinas e sistemas diferentes. A equipe precisa decidir quais artefatos gerar, como organizá-los e como orientar quem fará o download.
  1. Quais informações sobre o ambiente do usuário precisam ser conhecidas antes de gerar um executável? Pesquise e explique por que a arquitetura do processador e o sistema operacional são relevantes.
  2. Considere quatro usuários: Windows x86-64, Windows ARM64, Linux x86-64 e Linux ARM64. Quantos artefatos sua equipe deveria prever inicialmente? Monte uma matriz de distribuição e justifique sua resposta.
    Sistema operacionalArquiteturaArtefato previstoUsuário atendido
  3. Por que não basta simplesmente entregar o código-fonte para todos? Explique a diferença entre o código mantido no repositório da equipe e o artefato entregue ao usuário.
  4. Onde entra o compilador no processo de build? Explique como o mesmo código-fonte pode ser usado para produzir artefatos destinados a arquiteturas diferentes. Relacione sua resposta aos conceitos de target e ISA.
  5. O que pode acontecer se a equipe publicar apenas uma versão x86-64 e um usuário utilizar ARM64? Pesquise as possíveis consequências e explique por que isso se torna um problema de compatibilidade e suporte.
  6. Como um projeto real pode automatizar essas diferentes compilações? Pesquise o conceito de matriz de builds em integração contínua e explique como combinações de sistema operacional e arquitetura poderiam ser geradas ou testadas automaticamente.
  7. Que informações você colocaria na página de download ou na documentação para evitar que o usuário escolha o arquivo errado? Proponha uma forma de nomear os artefatos e de orientar o usuário sobre qual versão utilizar.
Entrega: produza um documento com as respostas às sete questões, a matriz de distribuição e as fontes consultadas. Ao final, sintetize em um parágrafo por que uma equipe pode manter uma única base de código e, ainda assim, distribuir vários artefatos diferentes.
