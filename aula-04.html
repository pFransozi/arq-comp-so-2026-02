Visão da aula

O software não termina no código-fonte

Código-fonte × máquina

A CPU não executa a abstração que escrevemos

Linguagens de alto nível oferecem nomes, tipos, estruturas de decisão, laços e funções para tornar o software compreensível e produtivo. O processador, porém, executa operações definidas pela sua arquitetura.

C · código-fonteexemplo mínimo
int maior(int a, int b) {
    if (a > b) {
        return a;
    }

    return b;
}
Para nós, a intenção é clara: comparar dois valores e devolver o maior.
a e b são nomes do programa

Durante a execução, os valores precisam existir em representações concretas, como registradores ou posições de memória.

if expressa uma decisão

No nível da máquina, essa decisão precisa ser realizada por operações elementares, como comparação, movimentação de dados e possível alteração do fluxo de execução.

return expressa uma intenção de alto nível

A forma exata de entregar o valor ao código chamador depende do alvo e das convenções usadas naquele ambiente.

Ideia central: uma construção da linguagem de programação não corresponde necessariamente a uma única instrução de máquina. Entre o que escrevemos e o que a CPU executa existe um processo de tradução.

Compilação

O compilador precisa saber para qual máquina está produzindo código

Compilar não é simplesmente “transformar C em Assembly”. O compilador precisa gerar uma representação compatível com um alvo. Esse alvo determina quais instruções e recursos podem ser usados.

1 · FonteCódigo-fonte

Expressa o algoritmo usando as abstrações da linguagem.

2 · FerramentaCompilador

Analisa o programa e produz código para um alvo escolhido.

3 · AlvoArquitetura / plataforma

Define restrições que o código gerado precisa respeitar.

4 · ResultadoCódigo de máquina / binário

Pode ser executado no ambiente para o qual foi produzido.

x86-64

Engenharia de Software

Target

Em ferramentas de build e pipelines, “target” identifica para qual arquitetura ou ambiente o artefato está sendo produzido.

Uma consequência prática: o mesmo repositório de código pode gerar artefatos diferentes. Quando um projeto publica versões x64 e ARM64, isso não é apenas uma decisão de empacotamento; há diferenças reais abaixo do código-fonte.

ISA · Instruction Set Architecture

A ISA é o contrato entre o software de baixo nível e o processador

O compilador não inventa livremente as operações da máquina. Ele produz instruções pertencentes ao conjunto que a arquitetura oferece. É nesse sentido que a ISA funciona como uma interface ou contrato.

O que esse contrato precisa definir?

Instruções disponíveisQuais operações o processador sabe interpretar.
Registradores visíveisQuais recursos de armazenamento rápido podem ser usados pelas instruções.
Formas de representar operandosComo instruções referenciam valores, registradores e memória.
Representações e tamanhos suportadosQuais formatos de dados fazem parte da arquitetura.

Limite didático

O que não precisamos dominar nesta aula

Para compreender compatibilidade de software, não precisamos transformar a aula em um curso de Assembly.

  • Não memorizar listas de instruções.
  • Não decorar nomes de todos os registradores.
  • Não estudar modos de endereçamento em detalhe.
  • Não programar aplicações extensas em Assembly.
ISA não é o processador inteiro. Dois processadores podem implementar a mesma ISA e possuir organizações internas diferentes. A Aula 03 já separou arquitetura e organização; aqui usamos essa distinção para entender por que um binário depende de um contrato arquitetural.

Mesmo fonte, alvos diferentes

x86-64 e ARM64 não precisam gerar as mesmas instruções

O comportamento desejado pelo programa pode ser o mesmo, mas cada arquitetura dispõe de seu próprio conjunto de instruções, registradores e regras. O Compiler Explorer permite tornar essa diferença observável sem exigir que a turma programe em Assembly.

Fonte

Uma função em C

Cmesmo código
int dobro(int x) {
    return x * 2;
}
Observação

Duas traduções possíveis

Compile a mesma função para um alvo x86-64 e para um alvo ARM64. As instruções, nomes de registradores e detalhes da saída podem mudar, embora a intenção do programa continue sendo “calcular o dobro”.

Não procure equivalência linha a linha. Procure evidências de que arquiteturas distintas oferecem vocabulários de máquina distintos.

32 × 64 bits

Por que aparecem rótulos como x86, x64 e ARM64 nos downloads?

Para Engenharia de Software, o ponto importante não é decorar toda a história dessas arquiteturas, mas reconhecer que o tamanho e o modelo arquitetural fazem parte do alvo para o qual um programa é construído.

x86 / 32-bit

Indica, em muitos contextos de distribuição, uma versão construída para o ambiente x86 de 32 bits.

x64 / x86-64

Indica uma versão construída para a extensão de 64 bits da família x86.

ARM64

Indica uma versão construída para a arquitetura ARM de 64 bits.

O que “64 bits” sugere?

Entre outras consequências arquiteturais, ambientes de 64 bits ampliam a capacidade de representação de endereços e usam registradores e convenções adequadas a esse modelo. Isso afeta compiladores, bibliotecas, formatos de binário e compatibilidade.

Não conclua que “64 bits = duas vezes mais rápido”. Largura arquitetural e desempenho são coisas diferentes. Desempenho será tratado com métricas e evidências, não apenas pelo rótulo da arquitetura.

Binário e plataforma

Conhecer a ISA é necessário, mas não suficiente para prever compatibilidade

Um programa compilado precisa encontrar não apenas uma CPU que compreenda suas instruções, mas também um ambiente compatível com o formato e as interfaces que ele espera usar.

Aplicação compiladao binário que queremos executar
Ambiente binárioformato do executável, convenções de chamada, bibliotecas e interfaces esperadas
Sistema operacionalfornece serviços, carregamento, processos, arquivos e outras abstrações
Arquitetura / ISAdefine as instruções que a CPU consegue interpretar
Hardwareimplementa a arquitetura e executa o programa
Plataforma-alvo: nesta aula usaremos o termo para lembrar que “onde o software executa” não é definido apenas pelo nome do processador. Arquitetura, sistema operacional e ambiente binário precisam ser compatíveis.
Cenário A · Windows x64 → Windows x64

A arquitetura e o sistema operacional podem ser compatíveis, mas ainda podem existir dependências de bibliotecas ou versões.

Conclusão: compatibilidade é provável, não automática em todos os casos.
Cenário B · Windows x64 → Linux x64

A ISA pode ser a mesma, mas o ambiente binário e as interfaces do sistema operacional são diferentes.

Conclusão: mesma ISA não significa mesmo binário.
Cenário C · Windows x64 → Windows ARM64

A arquitetura muda. O binário original contém instruções produzidas para outra ISA, salvo quando o ambiente fornece algum mecanismo de tradução ou emulação.

Conclusão: arquitetura-alvo importa.
Cenário D · Código-fonte portátil

O mesmo fonte pode ser recompilado para diferentes alvos quando a linguagem, bibliotecas e dependências usadas oferecem suporte adequado.

Conclusão: portabilidade do fonte é diferente de portabilidade do binário.
ABI, sem aprofundamento: em sistemas reais existe também uma Interface Binária de Aplicação (ABI), que estabelece convenções para que código compilado interaja corretamente com bibliotecas e com o sistema. Basta reconhecer sua existência; detalhes de ABI não são objetivo desta aula.
