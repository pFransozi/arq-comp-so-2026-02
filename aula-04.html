Do código-fonte à execução

Na aula anterior vimos a CPU buscar e executar instruções. Agora vamos conectar esse modelo ao código que escrevemos: como nomes, valores e operações de uma linguagem de programação chegam a uma forma que o processador consegue executar?

Visão da aula

Da linguagem que usamos às operações que a máquina executa

Esta não é uma aula de Assembly nem de compiladores. O objetivo é construir uma ponte entre programação e arquitetura: reconhecer representações diferentes do mesmo problema e acompanhar um exemplo simples até a execução.

Paramos na instrução

Na máquina didática, a CPU buscava, interpretava e executava operações como LOAD, ADD e STORE. Hoje a pergunta muda: de onde essas operações vêm quando escrevemos um programa?

A CPU entende diretamente uma linha como resultado = a + b?
Uma variável é o seu nome, o seu valor ou o lugar onde o valor está armazenado?
Uma linha de código de alto nível corresponde necessariamente a uma única instrução de máquina?
Se o mesmo código roda em processadores diferentes, as instruções precisam ser idênticas?
Antes de continuar, escreva uma hipótese: qual é o caminho entre uma expressão escrita por um programador e uma operação realizada pela CPU?
Primeira representação

O código que escrevemos não é a instrução que a CPU executa

Linguagens de alto nível foram criadas para que possamos expressar algoritmos usando nomes, tipos, estruturas e funções compreensíveis para programadores. O processador, porém, executa instruções definidas pela arquitetura da máquina.

exemplo.cC
int a = 7;
int b = 5;
int resultado = a + b;

printf("%d\n", resultado);
Código-fonteExpressão escrita pelo programador.
→
TraduçãoCompilador, interpretador ou runtime participa da preparação.
→
InstruçõesOperações reconhecidas pela arquitetura.
→
CPUBusca, decodifica e executa.
Modelo simplificado. Compiladores, interpretadores, runtimes, sistemas operacionais e formatos executáveis podem formar percursos diferentes. Nesta aula, o foco está apenas na ideia comum: em algum nível, o trabalho precisa chegar a operações que o processador consegue executar.

Um programa compilado

Em C, um compilador pode traduzir o código-fonte e gerar código executável para uma arquitetura alvo.

C→compilador→executável→CPU

Um programa executado por um runtime

Em Python, o código é executado com participação do interpretador/runtime. Ainda assim, o computador físico continua executando instruções de máquina.

Python→runtime→SO→CPU

Segunda representação

Uma variável precisa ter um valor disponível em algum lugar

Para conectar programação e arquitetura, vamos separar três ideias que costumam aparecer misturadas: nome, valor e endereço.

Nome

a é um identificador usado no código-fonte para nos referirmos a um dado.

Valor

7 é o conteúdo associado a a neste instante do exemplo.

Endereço

0x1000 representa, de forma didática, uma posição onde esse conteúdo pode estar armazenado.

VariávelEndereço fictícioConteúdo
a0x10007
b0x10045
resultado0x1008?
Endereços didáticos. Os valores 0x1000, 0x1004 e 0x1008 são apenas uma representação para raciocinar. Ainda não estamos estudando endereço virtual, endereço físico, stack, heap ou alocação real de um compilador.
Se a = 7, então a, 7 e 0x1000 significam a mesma coisa? Explique a diferença entre os três.
Terceira representação

Uma expressão pode se transformar em várias operações elementares

Vamos usar uma linguagem de máquina didática. Ela não representa exatamente x86 ou ARM. Serve apenas para enxergar a decomposição da expressão em carregar dados, operar e armazenar o resultado.

resultado = a + b ↓ movimentar → operar → guardar
LOAD R1, [0x1000]Carregue em R1 o valor associado a a.
LOAD R2, [0x1004]Carregue em R2 o valor associado a b.
ADD R3, R1, R2Some os valores de R1 e R2 e coloque o resultado em R3.
STORE [0x1008], R3Guarde na posição de resultado o valor presente em R3.
Onde entram os registradores?

A CPU mantém valores temporários muito perto das unidades de execução

Registradores são pequenas áreas de armazenamento internas ao processador. Neste exemplo, eles ajudam a manter os operandos e o resultado temporário durante a operação.

Sem perder as camadas

O programa não executa isoladamente

O rastreamento anterior abriu somente um pequeno trecho da execução dentro da CPU. No sistema real, outras camadas continuam participando. O sistema operacional fornece abstrações e gerencia recursos; a aplicação não controla diretamente todo o hardware.

Do código à execução — leitura guiada

A atividade pode ser realizada sem instalar compilador ou simulador. Trabalhe com as representações fornecidas, formule hipóteses antes de consultar fontes externas e registre uma explicação coerente do percurso.

1

Preveja o resultado

trechoC
int x = 4;
int y = 3;
int z = x * 2 + y;
  • Qual é o valor final de z?
  • Quais operações precisam ocorrer?
  • Quais valores precisam estar disponíveis?
2

Separe nome, endereço e valor

Considere o mapa didático:

  • x → 0x2000 → 4
  • y → 0x2004 → 3
  • z → 0x2008 → ?

Explique o que cada parte representa e por que esses três elementos não são equivalentes.

3

Leia as operações

Use a sequência didática:

  • LOAD R1,[0x2000]
  • MUL R2,R1,2
  • LOAD R3,[0x2004]
  • ADD R4,R2,R3
  • STORE [0x2008],R4

Monte uma tabela de passos e indique em que momento o valor final aparece em um registrador e em que momento chega à memória.

Checklist de saída

O que você precisa conseguir explicar

Não é necessário memorizar uma sintaxe de Assembly. A meta é sair da atividade sabendo conectar representações e explicar o caminho geral de execução.

Código-fonte e instrução de máquina não são a mesma representação.
Compiladores, interpretadores e runtimes participam de maneiras diferentes do caminho até a execução.
Nome de variável, valor e endereço representam conceitos distintos.
Registradores mantêm valores temporários durante a execução.
Uma expressão simples pode exigir várias operações elementares.
Carregar, operar e armazenar são etapas diferentes.
A CPU continua realizando o ciclo de busca, interpretação e execução.
Arquiteturas diferentes podem oferecer conjuntos de instruções diferentes.
Ponte para a próxima aula: se dois processadores podem executar o mesmo programa, mas possuem conjuntos de instruções e organizações diferentes, o que muda quando comparamos x86/x64 e ARM?
