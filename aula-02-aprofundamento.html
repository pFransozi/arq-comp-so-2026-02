Parte I · Da descrição à atividade

O que significa executar um programa?

Escrever um programa e executar um programa são situações diferentes. A primeira produz uma descrição; a segunda coloca essa descrição em relação com recursos reais do sistema computacional.

Código não é execução

Um arquivo de código-fonte contém uma representação de operações que desejamos realizar. Enquanto está armazenado, ele é uma estrutura de informação: possui bytes, organização sintática e significado para ferramentas e programadores, mas não está, por si só, consumindo tempo de processador para realizar o trabalho descrito.

A execução começa quando o sistema cria as condições para que aquelas operações sejam efetivamente realizadas. Isso exige carregar código e dados, estabelecer um contexto de execução, reservar ou disponibilizar memória, obter tempo de processador e, quando necessário, solicitar serviços relacionados a arquivos, terminal, rede ou outros dispositivos.

Uma ação aparentemente simples mobiliza várias camadas

Quando uma pessoa solicita a execução de um programa, costuma enxergar uma relação direta entre comando e resultado. Do ponto de vista do sistema, há muito mais acontecendo. O programa pode depender de um interpretador ou runtime, o sistema operacional precisa organizar recursos e o hardware precisa realizar operações físicas sobre instruções e dados.

É por isso que a pergunta “quem executa o programa?” não possui uma boa resposta se escolhermos apenas uma camada. A CPU executa instruções de máquina; o sistema operacional controla e oferece recursos; o runtime transforma e coordena operações próprias da linguagem; e a aplicação expressa a lógica que queremos realizar. A execução observada resulta da cooperação entre esses níveis.

Distinção central: o programa descreve trabalho; a execução é o trabalho acontecendo dentro de um sistema que fornece processador, memória e mecanismos de entrada/saída.

Pergunta da aula

O que acontece entre executar um programa e produzir um resultado?

Uma primeira resposta

O código precisa ser colocado em um contexto no qual instruções possam ser executadas, dados possam ser mantidos e recursos externos possam ser acessados de forma controlada.

Por que isso importa para Engenharia de Software?

Requisitos como desempenho, compatibilidade, uso de memória, persistência e interação com dispositivos dependem de camadas que ficam abaixo da lógica da aplicação.

Parte II · Um modelo para raciocinar

Aplicação, runtime, sistema operacional e hardware

O modelo em camadas usado na Aula 02 separa responsabilidades para tornar a execução compreensível. Ele não afirma que cada camada funciona isoladamente.

Aplicação

Expressa a lógica do problema e utiliza as abstrações fornecidas pelas camadas inferiores.

Runtime

Oferece mecanismos próprios do ambiente de execução da linguagem, como representação de objetos, execução de operações, bibliotecas e integração com serviços do sistema.

Sistema operacional

Organiza o uso dos recursos físicos, fornece abstrações e estabelece mecanismos de proteção e compartilhamento.

Hardware

Realiza operações físicas sobre instruções e dados por meio de processador, memória, controladores e dispositivos de entrada/saída.

Por que dividir em camadas?

Sem abstrações, cada aplicação teria de conhecer detalhes específicos de processadores, dispositivos de armazenamento, controladores de vídeo, teclados, redes e muitos outros componentes. A divisão em níveis reduz essa complexidade ao estabelecer interfaces e responsabilidades.

A aplicação pode pedir para abrir um arquivo sem conhecer o protocolo elétrico do dispositivo de armazenamento. Um runtime pode criar uma estrutura de dados sem exigir que o programador manipule diretamente cada endereço físico de memória. O sistema operacional pode fornecer a ideia de “processo” ou “arquivo” como abstrações mais estáveis do que os detalhes do hardware.

Abstrair não significa esconder tudo

As camadas reduzem detalhes, mas não eliminam consequências. Uma aplicação continua sendo afetada pela quantidade de memória disponível, pela velocidade do processador, pela latência de entrada/saída e pelas decisões do sistema operacional. O engenheiro de software não precisa controlar diretamente todos esses mecanismos, mas precisa compreender que eles condicionam o comportamento do software.

O runtime não é uma camada universal

O termo runtime é particularmente útil em ambientes como Python, Java, .NET e JavaScript, nos quais existe uma infraestrutura de execução relevante entre o código escrito pelo programador e os serviços do sistema operacional. Em outros cenários, como programas nativos compilados, essa fronteira pode parecer menos evidente. O modelo continua útil, mas as divisões concretas variam conforme linguagem, compilador, bibliotecas e plataforma.

O modelo é uma simplificação

Setas como “Aplicação → Runtime → SO → Hardware” ajudam a pensar em dependências, mas a execução real envolve retornos, interrupções, buffers, caches, bibliotecas, controladores e múltiplas interações em ambas as direções.

Interface

Uma camada pode usar serviços de outra sem conhecer toda a sua implementação interna. Essa separação é um dos princípios que tornam sistemas complexos administráveis.

Parte III · Programa em execução

Programa e processo não são a mesma coisa

A distinção entre uma descrição armazenada e uma atividade em andamento é fundamental para compreender o papel do sistema operacional.

Programa

Uma descrição armazenada

Código e dados organizados de modo que possam ser carregados ou interpretados para realizar uma tarefa.

Processo

Uma execução em andamento

Uma instância ativa que possui contexto, memória associada, estado de execução e relação com recursos administrados pelo sistema operacional.

Do arquivo para uma entidade gerenciada

Um mesmo programa pode ser executado mais de uma vez. Cada execução precisa ser distinguida das outras porque pode estar em um ponto diferente do código, manipular dados diferentes e possuir recursos diferentes. O conceito de processo permite ao sistema operacional representar e administrar essas execuções separadamente.

O processo não é apenas o conteúdo do programa copiado para a memória. Ele inclui também informações necessárias para continuar a execução: onde ela está, quais recursos estão associados, qual memória pertence àquela execução e outros elementos de contexto.

Processos tornam o compartilhamento controlável

Em um computador comum, muitas execuções coexistem. Navegador, editor, terminal, serviços do sistema e aplicações diversas disputam processador, memória e entrada/saída. O sistema operacional precisa manter separação suficiente para que uma execução não trate os recursos de outra como se fossem seus.

Essa ideia prepara os temas de gerenciamento de processos que serão aprofundados mais adiante. Aqui basta compreender que processo é a abstração usada para tratar uma execução como uma entidade administrável.

Neste ponto da disciplina: não é necessário detalhar estados de processo, estruturas internas do kernel ou algoritmos de escalonamento. O objetivo é apenas entender por que “programa” e “programa em execução” são conceitos distintos.

Uma consequência importante

Fechar um processo não apaga necessariamente o programa que o originou. O programa continua armazenado e pode iniciar uma nova execução.

Outra consequência

Duas execuções do mesmo programa podem ter estados diferentes porque cada processo representa uma atividade independente.

Parte IV · A camada intermediária

O sistema operacional como abstração e gerenciador de recursos

O sistema operacional permite que programas utilizem o computador sem assumir diretamente toda a complexidade e todo o risco do acesso ao hardware.

Abstração

Uma máquina mais conveniente

Processos, arquivos, diretórios e outros conceitos oferecem interfaces mais regulares do que a manipulação direta de cada mecanismo físico.

Gerência

Recursos precisam ser coordenados

Processador, memória e dispositivos são finitos e compartilhados. O sistema operacional organiza seu uso e estabelece regras de proteção.

Dois papéis que se complementam

Uma forma clássica de compreender sistemas operacionais combina dois pontos de vista. No primeiro, o SO oferece uma interface mais simples e abstrata sobre a máquina física. No segundo, administra recursos para que diferentes programas possam utilizá-los com segurança e eficiência.

Esses papéis aparecem juntos na execução de tarefas comuns. Ao criar um arquivo, por exemplo, a aplicação trabalha com uma abstração de alto nível. Internamente, o sistema operacional precisa verificar permissões, administrar estruturas do sistema de arquivos, coordenar buffers e interagir com mecanismos de entrada/saída.

Proteção é parte da arquitetura de execução

Se qualquer programa pudesse alterar livremente qualquer região de memória ou controlar diretamente qualquer dispositivo, uma falha local poderia comprometer todo o sistema. Por isso, processadores modernos e sistemas operacionais trabalham com mecanismos que distinguem operações permitidas a aplicações comuns de operações reservadas ao núcleo do sistema.

A separação entre espaço de usuário e espaço do núcleo pode ser entendida, neste momento, como uma fronteira de privilégio: aplicações executam com acesso limitado e solicitam ao sistema operacional operações que exigem autoridade maior sobre recursos compartilhados.

O SO não executa toda instrução da aplicação

É importante evitar outro extremo. O sistema operacional não fica interpretando, uma a uma, todas as instruções normais do programa. A maior parte da execução de código de usuário acontece diretamente no processador com os privilégios apropriados. O SO intervém quando precisa fornecer serviços, lidar com eventos, organizar recursos ou retomar o controle da máquina.

Processador

O SO decide e coordena o uso do tempo de CPU entre atividades concorrentes, embora a execução física das instruções ocorra no processador.

Memória

O SO acompanha e protege o uso da memória por diferentes processos, oferecendo a cada execução uma visão organizada de seu espaço de endereçamento.

Entrada/saída

O SO oferece interfaces comuns para dispositivos distintos e utiliza drivers e controladores para realizar operações concretas.

Parte V · A base física da execução

Processador, memória e entrada/saída têm papéis diferentes

O hardware não é um bloco único. A execução depende da cooperação entre componentes especializados em processar, manter informação temporariamente e comunicar-se com o ambiente externo.

CPU

Executar instruções

Busca, interpreta e realiza operações definidas pela arquitetura do conjunto de instruções.

Memória

Manter o trabalho ativo

Disponibiliza instruções e dados que precisam ser acessados durante a execução.

Armazenamento

Persistir informação

Mantém programas e dados mesmo quando a execução termina ou a energia é desligada.

E/S

Interagir com o exterior

Conecta o sistema a dispositivos, redes, terminais, sensores e outras fontes ou destinos de informação.

A CPU executa instruções de máquina

Programadores normalmente trabalham com linguagens de nível mais alto do que a linguagem diretamente compreendida pelo processador. Entre o código-fonte e a CPU existem processos de tradução, interpretação, compilação, bibliotecas e runtimes, dependendo da tecnologia utilizada.

No nível do processador, a execução ocorre por meio de instruções definidas pela arquitetura da máquina. Em uma visão introdutória, podemos imaginar um ciclo contínuo no qual uma instrução é obtida, decodificada e executada, alterando registradores, dados ou o fluxo de execução.

Memória não é sinônimo de armazenamento

A memória principal funciona como espaço de trabalho para a execução. Instruções e dados precisam estar disponíveis com baixa latência para que o processador possa utilizá-los. Já o armazenamento persistente prioriza a conservação de informação ao longo do tempo.

Essa diferença ajuda a responder uma pergunta frequente: um programa pode existir no armazenamento sem estar em execução; quando executado, partes relevantes de seu código e de seus dados passam a participar de uma estrutura de memória ativa associada ao processo.

Entrada e saída conectam a execução ao mundo

Uma operação de entrada/saída ocorre quando o sistema precisa trocar informação com algo além do processamento interno imediato da CPU. Ler um arquivo, escrever no terminal, receber dados de rede ou acessar um dispositivo são exemplos de E/S.

Essas operações têm características diferentes das operações puramente computacionais. Dispositivos possuem velocidades, protocolos e formas de controle próprias. Por isso, controladores, drivers e o sistema operacional formam uma cadeia que separa a aplicação dos detalhes físicos de cada periférico.

Limite deliberado: a Aula 03 abrirá a camada de hardware e estudará com mais detalhe CPU, memória, interconexões, programa armazenado, arquiteturas von Neumann e Harvard e ciclo de instrução. Aqui esses conceitos aparecem somente no nível necessário para compreender a execução de ponta a ponta.

Quem faz a conta?

No fim da cadeia, operações aritméticas e lógicas são realizadas por circuitos do processador; o código de alto nível especifica o que desejamos fazer, mas não é executado literalmente como texto.

Onde ficam os dados?

Durante a execução, dados são mantidos em diferentes níveis da hierarquia de memória. A visão simplificada desta aula destaca a memória principal; caches e detalhes internos serão aprofundados depois.

Parte VI · Atravessando a fronteira

Serviços do sistema operacional e chamadas de sistema

Aplicações precisam de um mecanismo controlado para solicitar operações que envolvem recursos protegidos ou compartilhados.

Solicitar é diferente de controlar diretamente

Quando uma aplicação deseja criar um arquivo, enviar dados pela rede ou obter alguma informação do sistema, ela normalmente não recebe permissão para manipular livremente o hardware correspondente. Em vez disso, utiliza interfaces que conduzem a uma solicitação ao sistema operacional.

A chamada de sistema é o mecanismo conceitual que permite essa transição controlada entre código de usuário e serviços oferecidos pelo núcleo. A forma concreta como uma linguagem chega até essa interface pode envolver bibliotecas, runtimes e APIs, mas a ideia fundamental permanece: certas operações precisam ser mediadas pelo sistema operacional.

Uma chamada de sistema muda o contexto da execução

Durante código comum de usuário, o processador executa com privilégios limitados. Ao solicitar um serviço do núcleo, ocorre uma transição controlada para código privilegiado do sistema operacional. Depois que o serviço é tratado — imediatamente ou após alguma espera — a execução pode retornar ao código da aplicação.

Essa transição ajuda a explicar por que a execução não é uma seta simples da aplicação para o hardware. O controle pode alternar entre aplicação, bibliotecas, runtime e núcleo muitas vezes ao longo de uma única tarefa.

APIs e chamadas de sistema não são sinônimos

Uma API é uma interface de programação apresentada ao desenvolvedor. Ela pode ser implementada inteiramente em uma biblioteca, pode chamar outras bibliotecas ou pode, em algum ponto, solicitar serviços do sistema operacional. Uma chamada de sistema é uma interface específica com o núcleo. Separar esses conceitos evita assumir que toda função de biblioteca atravessa necessariamente a fronteira do kernel.

Exemplo conceitual: arquivo

A aplicação expressa a intenção de abrir ou gravar; bibliotecas e runtime organizam a chamada; o SO valida e gerencia o recurso; drivers e hardware realizam as operações necessárias no dispositivo.

Exemplo conceitual: terminal

“Imprimir” texto não significa desenhar diretamente pixels na tela. A saída percorre abstrações e componentes até chegar ao destino visível.

Parte VII · Reconstruindo o percurso

Uma visão integrada da execução

Podemos agora reconstruir o percurso apresentado em sala sem confundir descrição, execução, abstração e mecanismo físico.

Código-fonte Programa Runtime / bibliotecas Processo Serviços do SO CPU · memória · E/S Resultado

O fluxo é conceitual, não cronológico

O diagrama acima organiza responsabilidades, mas não deve ser interpretado como sete etapas que acontecem uma única vez. Depois que um processo existe, a execução pode alternar repetidamente entre código da aplicação, runtime, bibliotecas e serviços do sistema operacional. A CPU continua executando instruções enquanto a memória fornece dados e a entrada/saída introduz eventos e esperas.

O resultado pode depender de recursos diferentes

Uma tarefa essencialmente aritmética pode depender principalmente de CPU e memória. Uma tarefa que lê muitos arquivos pode passar grande parte do tempo aguardando entrada/saída. Uma aplicação interativa pode alternar pequenos períodos de processamento com longas esperas por eventos externos. Em todos os casos, a lógica do software é a mesma dimensão do problema, mas o comportamento da execução depende também da plataforma.

Da abstração ao requisito de software

Essa visão é importante porque requisitos não funcionais frequentemente atravessam camadas. “Responder rapidamente”, “usar pouca memória”, “funcionar em determinada arquitetura” ou “persistir dados com segurança” não são propriedades explicadas apenas pelo algoritmo da aplicação. Elas dependem das interações entre software e sistema computacional.

Uma boa pergunta de engenharia

Qual camada possui a responsabilidade principal pelo comportamento que estou observando — e quais outras camadas podem condicioná-lo?

Evite explicações monocausais

“É a CPU”, “é o Python” ou “é o sistema operacional” costumam ser respostas incompletas quando a pergunta é sobre o percurso inteiro de uma aplicação.

Parte VIII · O que conseguimos observar

Execução e evidência não são a mesma coisa

A execução possui muitos eventos internos; logs, métricas, testes e rastros são maneiras diferentes de produzir sinais sobre o que aconteceu.

Conceito Pergunta principal O que representa Limite
Teste O comportamento atende ao que era esperado? Uma verificação de propriedade, resultado ou condição. Um teste aprovado não descreve todo o caminho percorrido internamente.
Log O que a aplicação ou componente decidiu registrar? Eventos selecionados pelo próprio software. Ausência de registro não significa ausência do evento.
Métrica Qual grandeza foi medida? Uma representação quantitativa de tempo, uso, volume ou outra propriedade. Precisa de contexto e condições de coleta para ser interpretada.
Rastro / trace Que sequência de interações foi observada? Eventos associados ao percurso de execução em determinado nível. Todo rastro é parcial: ele enxerga a camada e os eventos que o mecanismo de observação consegue capturar.

Observar exige escolher um nível

Uma aplicação pode registrar que iniciou uma tarefa, enquanto o sistema operacional observa abertura de arquivos e o hardware realiza inúmeras instruções que não aparecem em nenhum desses registros. Cada evidência corresponde a um ponto de observação diferente.

Isso significa que não devemos confundir “o que conseguimos medir” com “tudo o que aconteceu”. Uma explicação técnica forte relaciona a evidência ao modelo do sistema e reconhece o nível no qual ela foi produzida.

O modelo orienta a interpretação

Se sabemos que abrir um arquivo depende de serviços do sistema operacional, um rastro de chamadas ao SO pode ser relevante para aquela pergunta. Se queremos comparar o custo computacional de uma rotina, métricas de tempo e uso de CPU podem ser mais adequadas. A escolha da evidência nasce da pergunta sobre a execução, não apenas da disponibilidade de uma ferramenta.

Princípio de leitura

Uma evidência é sempre uma representação parcial do sistema. Antes de concluir, pergunte: de qual camada este sinal vem?

Parte IX · O que foi simplificado

O modelo da Aula 02 é útil porque deixa detalhes para depois

Compreender um sistema complexo exige escolher um nível de abstração. Alguns mecanismos foram propositalmente apenas mencionados nesta etapa.

01 Detalhes internos da CPU

Registradores específicos, unidade de controle, ALU, barramentos internos e execução detalhada serão tratados ao abrir a camada de hardware.

02 Arquiteturas de memória

Cache, hierarquia, endereçamento e memória virtual exigem modelos próprios e aparecerão em momentos posteriores.

03 Escalonamento

A ideia de que processos compartilham CPU é suficiente agora; políticas e algoritmos de escalonamento serão aprofundados depois.

04 Threads e concorrência

Uma execução pode conter múltiplos fluxos, mas isso não é necessário para compreender o modelo básico de processo usado nesta leitura.

05 Drivers e controladores

Foram apresentados como ponte com dispositivos; protocolos, interrupções e detalhes de E/S ficam para o aprofundamento específico.

06 Compilação e interpretação

O caminho entre código de alto nível e instruções de máquina varia entre linguagens e plataformas e merece uma discussão própria.

Por que não explicar tudo agora? Porque um modelo é útil quando destaca relações relevantes para uma pergunta. Na Aula 02, a pergunta é como software, sistema operacional e hardware participam da execução. A próxima aula muda a escala e pergunta como a camada de hardware está organizada internamente para realizar essa execução.

Parte X · Síntese

Da aplicação ao hardware: o que precisa ficar

Ao terminar esta leitura, a ideia central não é decorar nomes de camadas, mas compreender responsabilidades e relações.

A Programa ≠ processo

Programa é uma descrição armazenada; processo representa uma execução ativa e gerenciada.

B Camadas reduzem complexidade

Aplicação, runtime, SO e hardware possuem responsabilidades diferentes e se comunicam por interfaces.

C SO abstrai e gerencia

O sistema operacional oferece uma máquina mais conveniente ao mesmo tempo em que coordena recursos compartilhados.

D CPU executa instruções

O processador realiza instruções de máquina; código de alto nível chega até esse nível por tradução e infraestrutura de execução.

E Memória sustenta a execução

Instruções e dados ativos precisam estar acessíveis durante a execução, enquanto armazenamento preserva informação de forma persistente.

F E/S atravessa fronteiras

Arquivos, terminal, rede e dispositivos exigem cooperação entre aplicação, SO, drivers, controladores e hardware.

A ponte para a Aula 03

Agora temos uma visão macroscópica do percurso: sabemos que uma aplicação se torna uma execução, que o sistema operacional organiza recursos e que o hardware realiza as operações físicas.

A próxima pergunta é mais específica: o que existe dentro da camada de hardware e como CPU, memória e entrada/saída cooperam para executar uma tarefa? Essa mudança de escala conduz ao estudo da organização do computador, do programa armazenado e do ciclo de instrução.
