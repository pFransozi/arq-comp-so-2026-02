Aula 04 · aprofundamento teórico

Do código-fonte ao binário e do binário à execução

Na aula principal observamos que o mesmo código-fonte pode gerar instruções diferentes para arquiteturas diferentes. Agora vamos abrir esse caminho: o que o compilador produz, como a ISA condiciona o resultado, onde entram ligação e carregamento e por que compatibilidade binária envolve mais do que apenas “ser x64” ou “ser ARM64”.

Pergunta central

O que precisa permanecer compatível para que um programa escrito em uma linguagem de alto nível possa ser transformado em um artefato que o sistema operacional carregue e o processador execute?

Responder a isso exige separar código-fonte, código objeto, executável, ISA, ABI e processo.

1 · Mapa da tradução

“Compilar” não é uma única transformação

Na linguagem cotidiana, dizemos que o código foi “compilado” e virou um executável. Para compreender o que acontece entre esses dois pontos, vale separar as representações intermediárias e as ferramentas que participam do processo.

1 · FonteCódigo-fontePrograma escrito em linguagem de alto nível.
2 · TraduçãoCompiladorConverte o programa para código objeto ou, em alguns casos, para linguagem de montagem.
3 · RepresentaçãoCódigo objetoCódigo de máquina produzido a partir de um módulo do programa.
4 · IntegraçãoLigadorCombina módulos objeto e resolve referências entre eles.
5 · ArtefatoExecutávelCódigo de máquina em forma adequada para ser carregado.
6 · ExecuçãoCarregador + SOColocam o programa em memória e preparam sua execução.

Por que separar essas etapas?

Stallings define o compilador como o programa que converte uma linguagem-fonte para linguagem de máquina, podendo também gerar linguagem de montagem como saída intermediária. O código objeto é a representação de linguagem de máquina criada pelo compilador ou montador. O ligador combina módulos objeto em um módulo carregável ou executável, e o carregador coloca esse programa na memória para execução.

Isso explica por que um projeto real pode ter vários arquivos-fonte, bibliotecas e módulos e ainda assim produzir um único artefato executável. O binário final é o resultado de uma cadeia de transformações, não uma cópia direta do código-fonte.

Distinção essencial

Código objeto e executável não são sinônimos. O primeiro pode ainda conter referências que precisam ser resolvidas pelo ligador.

Outra distinção

Um executável ainda é um arquivo. Ele só se torna parte de uma execução quando o sistema o carrega e cria o estado necessário para executá-lo.

2 · Código de alto nível e código de máquina

O compilador precisa reconstruir a intenção usando operações da máquina

Uma linguagem de alto nível oferece estruturas que não correspondem diretamente a instruções individuais do processador. O trabalho do compilador é expressar o comportamento do programa utilizando as operações disponíveis no alvo escolhido.

Cexemplo de alto nível
int maior(int a, int b) {
    if (a > b) {
        return a;
    }
    return b;
}
Comparar

A máquina precisa produzir uma operação que permita decidir a relação entre os dois valores.

Controlar o fluxo

A decisão do if precisa ser representada por operações capazes de escolher o caminho de execução.

Movimentar valores

Os operandos e o resultado precisam estar em locais que as instruções possam referenciar.

Retornar

A execução precisa seguir as regras do ambiente binário usado para transferir o resultado e continuar o programa.

Não existe correspondência fixa entre linha de código e instrução

Stallings destaca que, diferentemente do montador, um compilador não trabalha com uma correspondência em que cada comando de entrada equivale necessariamente a uma única instrução de máquina ou a uma sequência fixa. Uma construção de alto nível pode exigir várias operações e sua tradução depende das escolhas do compilador e da arquitetura-alvo.

Por que observar Assembly continua sendo útil?

A linguagem de montagem é uma representação simbólica das instruções de máquina. Ela é mais legível do que a representação binária e permite observar quais operações, registradores e referências estão sendo usados sem precisar interpretar diretamente os bits da instrução.

Esse é exatamente o papel do Compiler Explorer na aula principal: não transformar a disciplina em um curso de Assembly, mas revelar a distância entre a expressão de alto nível e a representação que respeita a máquina-alvo.

3 · ISA por dentro

A ISA define mais do que uma lista de nomes de instruções

Stallings apresenta a arquitetura do conjunto de instruções como a interface entre hardware e software. Para compreender por que dois targets geram saídas diferentes, precisamos olhar para os elementos que compõem esse contrato.

Repertório de operaçõesQuais operações a máquina oferece e qual é o nível de complexidade dessas operações.
Tipos de dadosQuais categorias de dados podem ser manipuladas diretamente pelas instruções.
Formato das instruçõesComo os bits são distribuídos para representar operação, operandos e demais campos necessários.
RegistradoresQuantos registradores podem ser referenciados pelas instruções e como são utilizados.
EndereçamentoComo uma instrução especifica onde encontrar seus operandos.

Uma instrução precisa representar operação e operandos

Dentro do computador, uma instrução é uma sequência de bits dividida em campos. Um desses campos identifica a operação; outros podem indicar registradores, valores ou referências necessárias para localizar os operandos.

CampoOperação
ReferênciaOperando A
ReferênciaOperando B
ReferênciaDestino

Representação didática. A quantidade e a organização dos campos variam de acordo com o conjunto de instruções e com o formato usado.

Onde um operando pode estar?

Memória

A instrução pode precisar fornecer informação suficiente para localizar um dado na memória.

Registrador

A instrução pode referenciar um registrador do processador pelo identificador definido pela arquitetura.

Imediato

O próprio valor pode estar contido em um campo da instrução.

Entrada/Saída

Em arquiteturas que usam instruções específicas para E/S, a instrução pode identificar o módulo ou dispositivo envolvido.

Conexão com a Aula 03

Na máquina didática, ADD 21 indicava uma operação e uma referência de operando. Agora estamos generalizando aquela ideia: arquiteturas reais precisam definir como operações e operandos são representados e localizados.

4 · Dois alvos reais

x86-64 e ARM64 expressam o mesmo software com contratos diferentes

Stallings utiliza as famílias Intel x86 e ARM como exemplos recorrentes de arquiteturas. A comparação ajuda a perceber que a diferença não é apenas estética: cada família define seu próprio conjunto de instruções, registradores, formatos e formas de endereçamento.

Família x86

x86-64

A evolução da arquitetura x86 é apresentada por Stallings como um exemplo de uma tradição de conjunto complexo de instruções, desenvolvida ao longo de sucessivas gerações de processadores.

Ao gerar código para x86-64, o compilador precisa utilizar instruções, registradores e formas de representação válidas para esse alvo.

Família ARM

ARM64 / AArch64

A arquitetura ARM é apresentada como um exemplo importante da tradição de computadores com conjunto reduzido de instruções e aparece em uma ampla variedade de sistemas.

Ao gerar código para ARM64, o compilador trabalha com outro repertório de instruções, outros registradores e outras regras arquiteturais.

O contraste RISC × CISC é contexto, não ranking

Para esta disciplina, o ponto central não é declarar uma família “melhor”. O que importa é reconhecer que arquiteturas diferentes oferecem contratos diferentes ao software e que o compilador precisa produzir uma representação válida para o alvo escolhido.

O que deve permanecer igual?

O comportamento definido pelo programa-fonte pode permanecer o mesmo. Uma função que soma, compara ou percorre uma estrutura continua descrevendo a mesma intenção lógica.

O que pode mudar?

A sequência de instruções, os registradores usados, o formato das instruções e as formas de referenciar operandos podem mudar. É por isso que o Assembly observado no Compiler Explorer pode ser bastante diferente quando alteramos o target.

Regra prática

Mesmo código-fonte não implica mesmo código de máquina.

Outra regra

Mesmo comportamento não exige a mesma sequência de instruções.

5 · API, ABI e ISA

Compatibilidade aparece em níveis diferentes

Uma das distinções mais úteis de Stallings é separar três interfaces: API, ABI e ISA. Elas ajudam a explicar por que “meu código compila” e “meu binário executa” são afirmações diferentes.

API

Application Programming Interface. É a interface usada por programas em linguagem de alto nível para acessar serviços por meio de bibliotecas. Stallings destaca que uma API favorece a portabilidade do software por recompilação em outros sistemas que aceitem essa API.

ABI

Application Binary Interface. Define um padrão para a portabilidade binária e a interface utilizada pelo programa para acessar o sistema operacional e os serviços disponíveis no ambiente.

ISA

Instruction Set Architecture. Define o repertório de instruções de linguagem de máquina que o computador pode seguir e constitui a fronteira arquitetural entre software e hardware.

Cenário 1Mesma API, outro alvo

O código-fonte pode continuar válido, mas precisa ser recompilado para gerar código de máquina compatível com a nova arquitetura.

Cenário 2Mesma ISA, outro ambiente binário

Compartilhar a arquitetura de processador não basta, por si só, para garantir que o mesmo executável use corretamente os serviços esperados pelo sistema.

Cenário 3ISA diferente

O código de máquina produzido para uma arquitetura não corresponde automaticamente ao repertório de instruções de outra arquitetura.

Fonte portátil × binário portátil

Essa distinção é especialmente importante em Engenharia de Software. A portabilidade do código-fonte pode ser obtida mantendo interfaces e recompilando. Portabilidade binária exige que o artefato já produzido seja compatível com o ambiente binário e com a arquitetura para os quais foi construído.

6 · Ligação e carregamento

O executável ainda precisa ser integrado e colocado em memória

O Apêndice B de Stallings detalha duas etapas que normalmente ficam escondidas quando apertamos “Build” ou “Run”: a ligação de módulos e o carregamento do programa.

Módulo objeto ACódigo traduzido de uma parte do programa.
Módulo objeto BOutro módulo compilado separadamente.
LigadorCombina módulos e resolve referências entre eles.
Módulo carregávelArtefato integrado, preparado para carregamento.
CarregadorPosiciona o programa na memória para execução.

Por que existem referências a resolver?

Um módulo pode chamar uma função ou acessar dados definidos em outro módulo. Antes da ligação, essa referência pode ser apenas simbólica. O ligador reúne os módulos e transforma essas referências em posições que façam sentido dentro do módulo carregável.

Ligação estática e ligação dinâmica

Stallings mostra que a resolução de referências externas pode ocorrer em momentos diferentes. Em uma estratégia de ligação antecipada, os módulos são combinados antes do carregamento. Na ligação dinâmica, parte dessa resolução é adiada e um módulo externo pode ser associado mais tarde, inclusive durante a execução.

O endereço final nem sempre é conhecido na compilação

Um programa pode ser preparado para ser carregado em diferentes regiões da memória. Por isso, Stallings distingue carregamento absoluto, carregamento relocável e carregamento dinâmico em tempo de execução.

MomentoO que pode acontecer com os endereçosConsequência
Compilação / montagemReferências simbólicas podem ser convertidas para uma forma apropriada ao módulo produzido.Parte do trabalho de localização já é resolvida antes do carregamento.
LigaçãoReferências entre módulos podem ser resolvidas quando os objetos são reunidos.O programa passa a formar um módulo carregável integrado.
CarregamentoEndereços relativos podem ser ajustados de acordo com a região em que o programa será colocado.O módulo pode ser carregado em locais diferentes da memória.
ExecuçãoAlgumas traduções de endereço podem ser realizadas dinamicamente com suporte do hardware.A posição física pode variar sem exigir que o programa use endereços físicos fixos.

7 · Do arquivo ao processo

Um executável no disco ainda não é um programa em execução

Tanenbaum e Bos ajudam a completar o percurso: o sistema operacional precisa transformar o arquivo executável em uma imagem de processo que possa receber tempo de CPU e usar memória e demais recursos.

TextoCódigo do programa.
DadosVariáveis e dados do processo.
Espaço livre / crescimentoRegião disponível no espaço de endereçamento.
PilhaEstado associado à execução de chamadas e dados temporários.

O papel de exec em sistemas UNIX

Tanenbaum descreve exec como a chamada que substitui a imagem de memória de um processo pelo arquivo executável indicado. Isso mostra uma diferença importante: o arquivo é um artefato armazenado; o processo é o estado de uma execução.

O sistema operacional participa da preparação dessa execução, enquanto o processador executa as instruções que compõem a nova imagem carregada.

Programa ≠ processo

O programa é a representação armazenada. O processo inclui o programa carregado e o estado necessário para sua execução. Essa distinção será retomada quando a disciplina entrar formalmente em processos e sistemas operacionais.

8 · Engenharia de Software

Compatibilidade precisa ser tratada como requisito de build e distribuição

A ementa da disciplina relaciona diretamente arquiteturas de hardware à construção de software compatível. A consequência prática é que arquitetura e ambiente de execução precisam aparecer nas decisões de projeto, build, teste e entrega.

BuildQual artefato estamos produzindo?

O processo de construção precisa gerar código adequado à arquitetura e ao ambiente binário que receberá o programa.

DistribuiçãoQuem pode usar este artefato?

Um release precisa tornar explícito para qual combinação de plataforma o arquivo foi preparado.

TesteO que realmente foi validado?

Testar uma combinação de arquitetura e ambiente não demonstra automaticamente compatibilidade com todas as demais combinações.

Uma única base de código pode produzir vários binários

Essa é uma consequência direta da separação entre código-fonte e código de máquina. O repositório pode manter uma mesma implementação em linguagem de alto nível enquanto o processo de construção produz artefatos diferentes para diferentes arquiteturas e ambientes.

O problema não termina na ISA

A ISA responde se o processador entende as instruções. A ABI responde se o binário está preparado para interagir com o ambiente esperado. A API ajuda a manter a portabilidade no nível do código-fonte. São níveis distintos de compatibilidade.

H9

Identificar necessidades tecnológicas específicas do projeto inclui reconhecer quais plataformas precisam ser suportadas.

H20

Distinguir arquiteturas de hardware permite planejar software compatível com os ambientes que realmente serão atendidos.

H21

Ferramentas e linguagens precisam ser empregadas considerando os contextos concretos de integração e execução.

Uma resposta-síntese possível

O código-fonte descreve o comportamento usando abstrações de uma linguagem. O compilador traduz esse comportamento para uma representação compatível com uma arquitetura-alvo; módulos objeto podem ser ligados em um executável; o carregador e o sistema operacional preparam esse artefato na memória; e o processador executa as instruções previstas pela ISA. A compatibilidade final depende, portanto, de várias interfaces e etapas.
