1 · Mapa da tradução

Do código que escrevemos ao programa que pode ser executado

Entre o arquivo-fonte escrito pelo programador e as instruções que o processador executa existem várias etapas. Cada uma recebe uma representação do programa, realiza uma transformação específica e produz algo que será usado pela etapa seguinte.

Comece por uma ideia simples

Quando escrevemos um programa em uma linguagem de alto nível, trabalhamos com nomes de variáveis, funções, estruturas de decisão e repetições. Essa forma é adequada para quem desenvolve o software, mas não é a representação que o processador executa diretamente.

O caminho até a execução pode ser entendido como uma sequência de transformações: o código-fonte é traduzido, os módulos produzidos são integrados, surge um executável e, por fim, esse arquivo é colocado em memória para que a execução possa começar.

Ideia-chave

O programa não “vira executável” de uma só vez. Ele passa por representações intermediárias, e cada etapa resolve um problema diferente.

Observe a mudança

Ao longo do percurso, a intenção escrita pelo programador vai sendo transformada em uma representação cada vez mais próxima da máquina que executará o programa.

1 · FonteCódigo-fonteÉ a representação escrita pelo programador em uma linguagem de alto nível.
2 · TraduçãoCompiladorTraduz o código-fonte para uma representação adequada à máquina-alvo. Em algumas cadeias, pode existir uma etapa intermediária em Assembly.
3 · MóduloCódigo objetoÉ código de máquina produzido para uma parte do programa, mas ainda pode conter referências que precisam ser resolvidas.
4 · IntegraçãoLigadorCombina módulos objeto e resolve referências entre partes compiladas separadamente.
5 · ArtefatoExecutávelÉ o programa em uma forma que pode ser carregada para execução no ambiente para o qual foi construído.
6 · ExecuçãoCarregador + SOColocam o executável em memória e preparam o estado necessário para iniciar sua execução.

Acompanhe um exemplo conceitual

Imagine um programa dividido em dois módulos: um contém a função principal e outro contém uma função de cálculo utilizada pelo primeiro. Cada módulo pode ser compilado separadamente, produzindo seu próprio código objeto.

Nesse momento, o módulo principal pode saber que precisa chamar a função de cálculo, mas ainda não possuir a informação final necessária para localizar essa função no programa completo. O ligador reúne os módulos e resolve essa relação, produzindo um único artefato executável.

O executável ainda é apenas um arquivo armazenado. Antes que a CPU possa executar suas instruções, o carregador precisa colocá-lo em memória e preparar sua execução. A distinção entre arquivo executável e processo será retomada mais adiante neste aprofundamento.

O que devemos guardar desta sequência?

Compilar é traduzir o código-fonte. Ligar é integrar módulos produzidos separadamente. Carregar é preparar o executável em memória para que ele possa começar a ser executado.

Essas etapas ajudam a explicar por que um projeto pode possuir vários arquivos-fonte e bibliotecas, mas entregar ao usuário um único executável — e também por que esse executável continua dependendo da arquitetura e do ambiente para os quais foi construído.

Código objeto ≠ executável

O código objeto já contém representação de máquina, mas ainda pode depender da integração realizada pelo ligador.

Executável ≠ execução

O executável é um artefato armazenado. Ele precisa ser carregado e preparado antes que suas instruções sejam efetivamente executadas.

2 · Código de alto nível e código de máquina

Do que escrevemos ao que o processador consegue executar

Quando programamos, normalmente descrevemos uma solução usando abstrações pensadas para pessoas. O processador, porém, não executa diretamente um if, um for, uma função ou o nome de uma variável. Antes da execução, essas construções precisam ser traduzidas para instruções pertencentes ao conjunto de instruções da máquina-alvo.

Mais próximo do programador

Código de alto nível

É o código escrito em linguagens como C, C++, Java ou Python. Ele permite expressar algoritmos com variáveis, expressões, funções, condições, repetições e outras estruturas que tornam o programa mais legível e mais fácil de desenvolver.

Nesse nível, muitos detalhes da máquina ficam escondidos. Ao escrever x = x + y, por exemplo, não precisamos indicar manualmente qual registrador receberá cada valor nem quais bits formarão a instrução executada.

Mais próximo do processador

Código de máquina

É a representação composta pelas instruções que o processador executa diretamente. Cada instrução é codificada em bits e segue as regras da ISA da arquitetura-alvo.

Essas instruções precisam indicar operações como somar, comparar, mover dados ou desviar a execução e também fornecer as informações necessárias para localizar seus operandos.

Assembly não é código de máquina

A linguagem Assembly é uma representação simbólica das instruções da máquina. Em vez de ler uma sequência de bits, usamos nomes para operações, registradores e referências. Ela continua dependente da arquitetura, mas é muito mais legível para nós. É por isso que o Compiler Explorer mostra Assembly: ele funciona como uma janela para observar a tradução sem exigir que interpretemos diretamente o código binário.

Uma operação simples já mostra a diferença entre os dois níveis

Considere a expressão abaixo. Para quem programa, ela descreve uma única intenção: somar o valor de y ao valor de x e guardar o resultado novamente em x.

Clinguagem de alto nível
x = x + y;
1 · Buscar o primeiro valor

A máquina pode precisar carregar o valor associado a x para um registrador.

2 · Realizar a soma

Uma instrução aritmética utiliza o valor de y e o valor já disponível para produzir o resultado.

3 · Guardar o resultado

O novo valor precisa ser colocado no local associado a x.

Uma linha de código de alto nível pode exigir várias instruções de máquina

Diferentemente do montador, um compilador não trabalha com uma correspondência fixa em que cada comando de entrada equivale necessariamente a uma única instrução de máquina ou a uma sequência predeterminada. Uma construção de alto nível pode exigir várias operações, e sua tradução depende das escolhas do compilador e da arquitetura-alvo.

Que tipos de trabalho a máquina precisa conseguir representar?

Para executar programas escritos em linguagens de alto nível, o conjunto de instruções precisa oferecer operações suficientes para decompor essas construções em ações executáveis pelo processador. Podemos organizar essas ações em quatro grupos úteis:

Processamento de dadosOperações aritméticas e lógicas, como somas, comparações e manipulações de bits.
Armazenamento de dadosOperações que movimentam valores entre registradores e memória.
Entrada e saídaOperações necessárias para que dados entrem no sistema ou sejam enviados para dispositivos e serviços externos.
ControleTestes e desvios que permitem alterar a próxima instrução executada, dando suporte a decisões, repetições e chamadas.

Agora observe uma estrutura que usamos o tempo todo

Uma condição parece simples no código-fonte, mas precisa ser decomposta em operações menores. Considere a função:

Cexemplo com decisão
int maior(int a, int b) {
    if (a > b) {
        return a;
    }
    return b;
}
Comparar

O processador precisa realizar uma operação que permita determinar a relação entre a e b.

Tomar uma decisão

O resultado da comparação precisa influenciar qual caminho da execução será seguido.

Selecionar o resultado

Dependendo da decisão, um dos dois valores precisa ser escolhido como resultado da função.

Continuar a execução

Concluída a função, o processador precisa prosseguir a partir do ponto adequado do programa.

O que observar no Compiler Explorer?

Não é necessário decorar instruções. Primeiro identifique o papel das operações que aparecem: movimentação de dados, cálculo, comparação, controle de fluxo e retorno.

Depois altere o target e compare novamente. A intenção do programa continua a mesma, mas os nomes das instruções, os registradores utilizados e a sequência produzida podem mudar porque outra ISA está sendo usada como alvo.

Pergunta útil

Qual parte do Assembly parece corresponder à comparação? Qual parte parece controlar a decisão?

Evite uma armadilha

Contar linhas de Assembly, sozinho, não explica se uma tradução é “melhor”. Instruções diferentes podem realizar quantidades diferentes de trabalho.

O ponto central desta seção

O código de alto nível descreve o que queremos que o programa faça usando abstrações adequadas ao desenvolvimento de software. O código de máquina descreve esse comportamento como instruções que um processador específico consegue executar. O compilador faz a ponte entre esses dois níveis.

3 · ISA por dentro

A ISA é o vocabulário e o conjunto de regras que a máquina entende

Depois de entender a diferença entre código de alto nível e código de máquina, precisamos olhar para a regra que conecta o software ao processador. A ISA — Instruction Set Architecture define quais instruções de máquina existem, quais dados elas podem manipular, como os operandos são indicados e como essas instruções são representadas.

Pense na ISA como um contrato entre software e hardware

O compilador não pode gerar qualquer operação que desejar. Para produzir código de máquina, ele precisa utilizar apenas as instruções, registradores, formatos e formas de endereçamento definidos pela arquitetura-alvo.

O processador, por sua vez, precisa implementar esse contrato: ao encontrar uma instrução válida, deve interpretá-la e produzir o efeito definido sobre registradores, memória e fluxo de execução.

Do lado do software

O compilador transforma o programa em instruções pertencentes à ISA escolhida como alvo.

Do lado do hardware

O processador reconhece essas instruções e executa os efeitos previstos pela arquitetura.

O que uma ISA precisa definir?

Não basta existir uma lista de nomes de instruções. A arquitetura precisa definir vários elementos para que uma instrução possa ser codificada, interpretada e executada.

OperaçõesQuais ações podem ser executadas: somar, subtrair, comparar, mover dados, carregar, armazenar, desviar a execução e outras.
Tipos de dadosQuais dados podem ser manipulados diretamente, como números, caracteres e valores lógicos representados em bits.
RegistradoresQuais registradores existem e como as instruções podem utilizá-los para armazenar operandos, resultados e informações de controle.
Formato das instruçõesComo os bits são organizados para identificar a operação e os operandos envolvidos.
EndereçamentoComo uma instrução indica onde encontrar seus dados: na própria instrução, em registradores ou na memória.
Fluxo de execuçãoComo a máquina determina a próxima instrução e como testes e desvios podem alterar a sequência normal do programa.

Abra uma instrução em partes

Uma instrução de máquina precisa fornecer ao processador informações suficientes para realizar uma operação. Conceitualmente, podemos lê-la respondendo a quatro perguntas.

O que fazer?Operação / opcode
Com quais dados?Operandos de entrada
Onde fica o resultado?Operando de resultado
O que vem depois?Próxima instrução

Representação conceitual. A quantidade de campos e a forma de codificação variam entre arquiteturas e formatos de instrução.

Exemplo 1 · uma soma entre registradores

Considere a pseudo-instrução abaixo. Ela não representa a sintaxe exata de x86 ou ARM; serve apenas para enxergar os elementos que uma instrução precisa expressar.

Pseudo-Assemblyexemplo didático
SOMAR R3, R1, R2
Operação

SOMAR representa o trabalho que deve ser realizado.

Operandos fonte

R1 e R2 representam os valores usados como entrada.

Resultado

R3 representa o local que receberá o resultado.

Próxima instrução

Se não houver desvio, a execução normalmente continua na instrução seguinte.

Uma instrução altera o estado da máquina

Antes da execução, os registradores possuem determinados valores. Depois da instrução, o valor de R3 muda para refletir o resultado da soma. O efeito esperado dessa operação faz parte do contrato definido pela ISA.

Exemplo 2 · onde o operando pode estar?

Outra parte importante da ISA é definir como localizar os operandos. O dado pode estar em locais diferentes, e a instrução precisa fornecer informação suficiente para encontrá-lo.

Imediato

O valor está dentro da própria instrução. Exemplo didático: SOMAR R1, R1, 5. Nesse caso, 5 é o operando imediato.

Registrador

O valor já está em um registrador. Exemplo didático: SOMAR R1, R1, R2.

Memória

A instrução precisa indicar como localizar um endereço de memória antes de usar o valor armazenado nele.

Base + deslocamento

Um endereço pode ser calculado combinando o conteúdo de um registrador-base com um deslocamento. Isso é útil para acessar variáveis locais, campos de estruturas e elementos de vetores.

Pseudo-Assemblyendereçamento didático
CARREGAR R1, [BASE + 8]
BASE

Representa um registrador que contém uma referência inicial.

+ 8

Representa um deslocamento usado para chegar ao dado desejado.

R1

Recebe o valor obtido da memória.

O mesmo objetivo pode ser expresso de formas diferentes

Arquiteturas diferentes podem oferecer repertórios de instruções, registradores, formatos e modos de endereçamento diferentes. Por isso, o compilador pode produzir sequências distintas para x86-64 e ARM64 mesmo quando o código-fonte descreve exatamente o mesmo comportamento.

Exemplo 3 · uma decisão também depende da ISA

Considere novamente uma condição como if (a > b). Em algum momento, a tradução precisa representar pelo menos duas tarefas: comparar os valores e alterar o fluxo de execução de acordo com o resultado.

A ISA precisa fornecer operações capazes de sustentar esse comportamento. Os detalhes podem variar entre arquiteturas: a forma de representar o resultado da comparação, a instrução usada para o desvio, os registradores envolvidos e a codificação das instruções não precisam ser iguais.

O que observar no Compiler Explorer?

Ao olhar para o Assembly, identifique primeiro as categorias, não tente decorar os nomes. Pergunte: há uma operação aritmética? Há movimentação entre memória e registradores? Aparece algum valor imediato? Há comparação ou desvio?

Depois altere o target. Observe quais elementos mudaram: registradores, instruções, quantidade de operações e formas de acessar dados. Essas diferenças são manifestações concretas de contratos de ISA diferentes.

Procure a operação

Qual instrução parece realizar o cálculo ou a comparação?

Procure os operandos

Eles aparecem como registradores, constantes ou referências à memória?

Procure o controle

Há alguma instrução que altere qual será a próxima instrução executada?

O ponto central desta seção

A ISA não descreve o programa que queremos construir. Ela descreve quais operações a máquina sabe executar e como essas operações devem ser expressas. O compilador transforma o comportamento escrito em linguagem de alto nível em uma sequência que respeita esse contrato.

4 · Dois alvos reais

O mesmo código-fonte pode precisar falar duas linguagens de máquina diferentes

Até aqui vimos que o compilador precisa gerar instruções válidas para uma ISA específica. Agora vamos tornar isso concreto comparando dois alvos reais: x86-64 e ARM64. O objetivo não é decorar instruções de nenhuma das duas arquiteturas, mas perceber o que muda quando o mesmo programa precisa ser executado por máquinas com contratos diferentes.

Por que comparar justamente essas duas famílias?

As famílias x86 e ARM são exemplos importantes de projetos de processador desenvolvidos a partir de tradições arquiteturais diferentes. A família x86 evoluiu durante muitas gerações mantendo compatibilidade com um conjunto amplo de instruções. A família ARM foi desenvolvida dentro da tradição de conjuntos reduzidos de instruções e com forte uso de registradores.

Para quem desenvolve software, a consequência prática é simples: a mesma intenção escrita em C pode resultar em sequências de instruções diferentes quando o alvo muda.

O que permanece

O algoritmo, as regras de negócio e o comportamento esperado do programa podem continuar exatamente os mesmos.

O que muda

As instruções disponíveis, os registradores, os formatos das instruções e as formas de acessar operandos dependem da arquitetura escolhida.

Família x86

x86-64

É uma evolução da família x86. Seu conjunto de instruções foi ampliado ao longo de várias gerações, preservando compatibilidade e incorporando novas capacidades.

Ao compilar para x86-64, o compilador precisa escolher instruções, registradores e formas de endereçamento pertencentes a esse contrato.

Família ARM

ARM64

A família ARM está associada historicamente à tradição RISC, com forte uso de registradores e formatos de instrução mais regulares.

Ao compilar para ARM64, o compilador trabalha com outro repertório de instruções, outros registradores e outras regras de codificação e acesso a dados.

RISC × CISC é uma forma de contextualizar, não de escolher um vencedor

Esses termos ajudam a entender tradições de projeto. Eles não devem ser usados como um ranking simples de desempenho. Para esta aula, o que importa é perceber que arquiteturas diferentes oferecem recursos e regras diferentes ao software.

Exemplo · a mesma função, dois targets

Considere uma função simples. Em linguagem de alto nível, a intenção é apenas somar dois valores e devolver o resultado.

Cmesmo código-fonte
int soma(int a, int b) {
    return a + b;
}
Target x86-64

O compilador seleciona registradores e instruções definidos pela ISA x86-64.

Target ARM64

O compilador precisa expressar a mesma soma usando registradores e instruções definidos pela ISA ARM64.

Resultado lógico

Nos dois casos, a função continua devendo produzir o mesmo resultado para as mesmas entradas.

O ponto importante não é o nome da instrução

Se em um target aparece uma instrução com determinado nome e no outro aparece outra, isso não significa que um programa “mudou de ideia”. Significa que o compilador expressou a mesma intenção usando o vocabulário disponível em cada ISA.

O que comparar quando o Assembly for diferente?

Em vez de tentar alinhar linha por linha, compare o papel das operações. Procure identificar onde cada versão realiza cálculo, movimenta dados, acessa memória e controla o fluxo.

RegistradoresOs nomes e a organização dos registradores mudam entre as arquiteturas.
OperaçõesUma mesma intenção pode ser implementada por instruções com nomes e capacidades diferentes.
EndereçamentoAs formas disponíveis para localizar operandos e acessar memória podem ser diferentes.
Formato das instruçõesA maneira como os bits representam operação e operandos também depende da arquitetura.
Quantidade de instruçõesUma sequência pode usar mais ou menos instruções sem que isso, isoladamente, indique melhor desempenho.

Experimento mental · o que acontece quando mudamos apenas o target?

Suponha que o código-fonte, o compilador e o nível de otimização permaneçam os mesmos. A única mudança é trocar o alvo de x86-64 para ARM64.

PermaneceAlgoritmo

A lógica escrita no código-fonte continua a mesma.

MudaRepresentação de máquina

O compilador passa a gerar instruções pertencentes a outra ISA.

ConsequênciaOutro artefato

O binário produzido para uma arquitetura não deve ser tratado como se fosse automaticamente executável pela outra.

Como observar isso no Compiler Explorer?

Use exatamente o mesmo trecho de C e gere primeiro para x86-64 e depois para ARM64. Não tente traduzir cada linha de Assembly. Observe padrões.

Compare os registradores utilizados, os nomes das operações, os acessos à memória e as instruções de controle. Depois tente explicar o que permaneceu semanticamente igual apesar das diferenças de representação.

O ponto central desta seção

Target não é apenas uma opção do compilador: ele define qual contrato de máquina a tradução precisa respeitar. x86-64 e ARM64 podem executar programas com o mesmo comportamento, mas o código de máquina produzido para cada uma é construído segundo regras diferentes.

5 · API, ABI e ISA

Compatibilidade aparece em níveis diferentes

Uma distinção importante é separar três interfaces: API, ABI e ISA. Elas ajudam a explicar por que “meu código compila” e “meu binário executa” são afirmações diferentes.

API

Application Programming Interface. É a interface usada por programas em linguagem de alto nível para acessar serviços por meio de bibliotecas. Uma API favorece a portabilidade do software por recompilação em outros sistemas que ofereçam a mesma interface.

ABI

Application Binary Interface. Define um padrão para a portabilidade binária e a interface utilizada pelo programa para acessar o sistema operacional e os serviços disponíveis no ambiente.

ISA

Instruction Set Architecture. Define o repertório de instruções de linguagem de máquina que o computador pode seguir e constitui a fronteira arquitetural entre software e hardware.

Cenário 1Mesma API, outro alvo

O código-fonte pode continuar válido, mas precisa ser recompilado para gerar código de máquina compatível com a nova arquitetura.

Cenário 2Mesma ISA, outro ambiente binário

Compartilhar a arquitetura de processador não basta, por si só, para garantir que o mesmo executável use corretamente os serviços esperados pelo sistema.

Cenário 3ISA diferente

O código de máquina produzido para uma arquitetura não corresponde automaticamente ao repertório de instruções de outra arquitetura.

Fonte portátil × binário portátil

Essa distinção é especialmente importante em Engenharia de Software. A portabilidade do código-fonte pode ser obtida mantendo interfaces e recompilando. Portabilidade binária exige que o artefato já produzido seja compatível com o ambiente binário e com a arquitetura para os quais foi construído.

6 · Ligação e carregamento

Compilar os arquivos ainda não basta para colocar o programa em execução

Em um projeto real, diferentes partes do programa podem ser compiladas separadamente. Isso produz módulos objeto, mas eles ainda precisam ser reunidos em um artefato coerente e, depois, colocados na memória. É nesse ponto que entram duas etapas diferentes: ligação e carregamento.

Primeiro separe os dois problemas

Ligação resolve o problema de integrar partes do programa. Um módulo pode usar uma função ou um dado definido em outro módulo; enquanto esses arquivos estão separados, essa referência pode existir apenas de forma simbólica.

Carregamento resolve outro problema: colocar o módulo carregável na memória e fazer com que suas referências de endereço façam sentido na posição em que ele foi colocado.

Ligador

Recebe módulos objeto, integra essas partes e resolve referências entre elas para produzir um módulo carregável.

Carregador

Coloca o módulo na memória principal e prepara seus endereços para que a execução possa começar.

Uma forma simples de lembrar

Ligação: “como estas partes se conectam?”. Carregamento: “onde este programa ficará na memória e como suas referências funcionarão ali?”.

Exemplo · dois arquivos que dependem um do outro

Imagine um programa dividido em dois arquivos. O primeiro contém a função principal; o segundo contém uma função de cálculo usada pelo primeiro.

Módulo A

main.c

Contém uma chamada para calcular_total().

Depois da compilação, main.o sabe que precisa dessa função, mas ainda pode ter apenas uma referência simbólica para ela.

Módulo B

calculos.c

Contém a implementação de calcular_total().

Depois da compilação, calculos.o contém o código correspondente a essa função.

main.oPossui uma referência ainda não resolvida para calcular_total().
calculos.oContém o código da função que será utilizada pelo primeiro módulo.
LigadorReúne os módulos e transforma a referência simbólica em uma referência válida dentro do módulo integrado.
Módulo carregávelPassa a conter as partes do programa em uma representação integrada.
CarregadorColoca esse módulo na memória e prepara os endereços usados durante a execução.
O que o ligador realmente resolveu?

Antes da ligação, o módulo A conhecia o nome da função de que precisava. Depois da ligação, essa dependência passa a apontar para uma posição concreta dentro do módulo carregável.

Agora aparece um segundo problema: em que endereço da memória o programa será colocado?

Nem sempre é desejável decidir, durante a compilação, a posição exata que um programa ocupará na memória. Se vários programas compartilham a memória, uma posição que estava livre em um momento pode não estar livre em outro.

Por isso, é comum trabalhar com endereços relativos. Em vez de dizer “este dado estará obrigatoriamente no endereço 4120”, o módulo pode representar algo como “este dado está 120 posições depois do início do programa”.

Exemplo conceitualrelocação
referência relativa = 120
base escolhida pelo carregador = 4000
endereço resultante = 4000 + 120 = 4120
Antes do carregamento

O módulo pode conter referências relativas ao seu próprio início.

Durante o carregamento

O carregador escolhe a posição inicial e ajusta as referências que precisam ser convertidas.

Depois do ajuste

As referências passam a fazer sentido na região de memória realmente ocupada pelo programa.

Três momentos possíveis para resolver os endereços

A diferença entre as estratégias está principalmente em quando a posição efetiva do programa e de suas referências é determinada.

Carregamento absolutoO módulo é preparado para uma posição específica da memória. Isso simplifica o carregamento, mas reduz a flexibilidade.
Carregamento relocávelO módulo usa referências relativas. Ao carregá-lo, o carregador ajusta essas referências de acordo com a posição escolhida.
Endereçamento em tempo de execuçãoAs referências permanecem relativas e a tradução para endereços efetivos é realizada dinamicamente durante a execução, com suporte do hardware.
Relocação não significa mover “qualquer número” do programa

O carregador precisa saber quais campos representam endereços que devem ser ajustados. Uma constante numérica usada pelo programa não pode ser tratada automaticamente como se fosse um endereço.

E onde entram bibliotecas?

Uma aplicação também pode depender de módulos externos, como bibliotecas. Essas dependências podem ser resolvidas em momentos diferentes.

Antes do carregamento

Ligação antecipada

Os módulos necessários são integrados antes de o programa ser carregado. O artefato resultante já traz as referências externas resolvidas para aquela composição.

Mais tarde

Ligação dinâmica

Algumas referências externas permanecem não resolvidas no módulo carregável e podem ser resolvidas no carregamento ou somente quando forem necessárias durante a execução.

Por que adiar a ligação pode ser útil?

Quando um módulo externo é mantido separadamente, uma versão atualizada dele pode ser incorporada sem exigir necessariamente que toda a aplicação seja recomposta do zero. Além disso, um mesmo código externo pode ser compartilhado por mais de uma aplicação.

O ponto importante é perceber que ligação dinâmica fala sobre quando uma dependência entre módulos é resolvida, enquanto carregamento relocável fala sobre onde um módulo será colocado na memória. São problemas diferentes.

Não confunda

Ligação conecta módulos. Relocação ajusta referências de endereço. Carregamento coloca o programa na memória.

Ordem conceitual

Compilar → produzir módulos objeto → ligar módulos → obter módulo carregável → carregar na memória → executar.

Do ponto de vista de Engenharia de Software

Essas etapas aparecem escondidas em comandos simples como Build ou Run, mas continuam existindo. Elas ajudam a explicar erros de símbolo não encontrado, dependências de bibliotecas, incompatibilidades entre artefatos e situações em que um executável existe no disco, mas ainda não está pronto para ser executado na memória.

O ponto central desta seção

Compilar traduz cada parte do código. Ligar integra essas partes e resolve dependências entre módulos. Carregar coloca o módulo resultante na memória e ajusta as referências necessárias para aquela execução. São etapas diferentes de uma mesma cadeia.

7 · Do arquivo ao processo

Um executável no disco ainda não é um programa em execução

O sistema operacional precisa transformar o arquivo executável em uma imagem de processo que possa receber tempo de CPU e utilizar memória e demais recursos.

TextoCódigo do programa.
DadosVariáveis e dados do processo.
Espaço livre / crescimentoRegião disponível no espaço de endereçamento.
PilhaEstado associado à execução de chamadas e dados temporários.

O papel de exec em sistemas UNIX

Em sistemas UNIX, exec substitui a imagem de memória de um processo pelo arquivo executável indicado. Isso evidencia uma diferença importante: o arquivo é um artefato armazenado; o processo é o estado de uma execução.

O sistema operacional participa da preparação dessa execução, enquanto o processador executa as instruções que compõem a nova imagem carregada.

Programa ≠ processo

O programa é a representação armazenada. O processo inclui o programa carregado e o estado necessário para sua execução. Essa distinção será retomada quando a disciplina entrar formalmente em processos e sistemas operacionais.

8 · Engenharia de Software

Compatibilidade precisa ser tratada como requisito de build e distribuição

A ementa da disciplina relaciona diretamente arquiteturas de hardware à construção de software compatível. A consequência prática é que arquitetura e ambiente de execução precisam aparecer nas decisões de projeto, build, teste e entrega.

BuildQual artefato estamos produzindo?

O processo de construção precisa gerar código adequado à arquitetura e ao ambiente binário que receberá o programa.

DistribuiçãoQuem pode usar este artefato?

Um release precisa tornar explícito para qual combinação de plataforma o arquivo foi preparado.

TesteO que realmente foi validado?

Testar uma combinação de arquitetura e ambiente não demonstra automaticamente compatibilidade com todas as demais combinações.

Uma única base de código pode produzir vários binários

Essa é uma consequência direta da separação entre código-fonte e código de máquina. O repositório pode manter uma mesma implementação em linguagem de alto nível enquanto o processo de construção produz artefatos diferentes para diferentes arquiteturas e ambientes.

O problema não termina na ISA

A ISA responde se o processador entende as instruções. A ABI responde se o binário está preparado para interagir com o ambiente esperado. A API ajuda a manter a portabilidade no nível do código-fonte. São níveis distintos de compatibilidade.

H20

Distinguir arquiteturas de hardware permite planejar software compatível com os ambientes que realmente serão atendidos.

H21

Ferramentas e linguagens precisam ser empregadas considerando os contextos concretos de integração e execução.

Uma resposta-síntese possível

O código-fonte descreve o comportamento usando abstrações de uma linguagem. A compatibilidade final depende, portanto, de várias interfaces e etapas.
